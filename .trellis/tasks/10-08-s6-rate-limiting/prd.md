# S6（收窄版）· 写端点限流

**立项理由**：S3 收尾时 OWASP 写操作清单第 5 条留下的唯一 ⚠️——写端点比读端点更需要限流，而当时一个都没有（记为缺口，归 S6）。按 2026-10-08 的范围裁定 P-5，这一条是上线前必做的四条之一。

**不在本阶段**（都写了触发条件，见文末）：缓存与失效、ETag、击穿防护、索引调优、指标、压测、负载均衡。

## 需求

- **S6-R1** Redis 定窗计数，**TTL 一定在第一位**：先 `SET key '0' NX EX <window>`（带 TTL），再 `INCR`。顺序反过来（先 INCR 再 EXPIRE）如果在两步之间进程死掉，会留下一个**没有 TTL 的键**，那个桶就永久粘住——这是本条唯一的理由，注释必须这样写，否则后来者会把它"整理"成直觉顺序。
- **S6-R2** 写请求按**已认证身份**分桶（`request.auth.sub`），不按 IP。这不是省事：nginx 之后所有访客的 `request.ip` 都是 `127.0.0.1`（见 S6-R4），按 IP 限流等于把所有用户并成一个桶，一个人刷新页面就能把全站限速。
- **S6-R3** `POST /api/v1/auth/github/start`（匿名）按客户端 IP 分桶。这是唯一需要在鉴权**之前**就限的入口，因为它能被完全匿名的流量打到。
- **S6-R4** Fastify 增加 `trustProxy: 'loopback'`。没有它，S6-R3 在部署形态下是错的：`request.ip` 会恒等于代理地址。取值 `'loopback'` 而不是 `true`，因为只应信任本机那台 nginx；直连 API 的非回环来源本来就不存在（`server.ts:53` 只绑回环）。
- **S6-R5** 超限返回 **429** + 既有错误信封（`code: 'RATE_LIMITED'`，errorHandler 已有 429 映射），并带 **`Retry-After`** 秒数。不带 `X-RateLimit-*` 头（没有消费者，加了就是没人读的接口）。
- **S6-R6** Redis 不可用时**限流器 fail-open 并 warn**，鉴权与 denylist 的既有行为**不许因此改变**。理由写进注释：限流是护住博客的盾，不是访问控制；fail-closed 会把一次 Redis 抖动放大成"全站 429"，那是比被刷更坏的故障。
- **S6-R7** 阈值走配置，**有默认值**（不是必填键——必填会把 CI 契约面扩大，而 CI 已经在 `env:` 里列了 10 个键）：
  - `RATE_LIMIT_WRITE_PER_MINUTE` 默认 **60**，作用于 articles / comments / uploads / import 的全部写方法
  - `RATE_LIMIT_ANON_PER_MINUTE` 默认 **10**，作用于 S6-R3 那个入口
  - 60 这个数字要写明依据：管理员一次批量导入 12 张图 = 24 次上传请求，`test:e2e` 与集成测试的写请求也在同一窗口里，30 会误伤合法动作。

## 验收标准

- [ ] 窗口内第 61 次写 → 429 + `RATE_LIMITED` + `Retry-After`；第 60 次仍 2xx（**边界两侧都测**，只测超限那一侧无法发现 off-by-one）
- [ ] 用户 A 打满不影响用户 B（同一时间窗内 B 仍成功）
- [ ] 匿名 start 超过 10 次 → 429；换一个 `X-Forwarded-For` 后不受影响（这条同时验 S6-R4 真的生效）
- [ ] Redis 抛错时：请求**照常通过**，且日志里有一条 warn（用抛错替身测，不去关容器）
- [ ] `Retry-After` 是正整数且 ≤ 窗口长度
- [ ] 阈值默认值在 CI 里不需要新增 env 键（`pnpm --filter api test` 全绿即为证）
- [ ] 变异：把 `SET ... NX EX` 与 `INCR` 顺序颠倒 → 有一条测试变红（证明 TTL 顺序是被守着的，不只是被注释着的）。若实在写不出这种测试（Redis 侧键状态才看得见），就直说"这条只能靠 Redis 键的 TTL 断言"，并真的去断言 TTL > 0
- [ ] 全部门禁绿：`-r lint`/`-r check`/`-r build`，`--filter api test` 从 **300 passed / 21 files** 只增不减；库回到 `7|2`、桶 0 对象

## 触发条件（现在不做，写清楚什么时候做）

- **缓存/ETag/击穿**：当公开读出现可测量的重复回源（现在 nginx + Next ISR 60s 已经把重复读挡在应用外）时再做。
- **索引调优**：当列表查询在真实数据量上出现在慢查询日志里；现在 6 篇 published 文章，任何"这是最优索引"的说法都没有依据。
- **指标/压测/负载均衡**：属 S7，触发条件同样是"单实例真的成了瓶颈"。
